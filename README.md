# RVKOMI Server Control

Установочный комплект Telegram-бота на основе `rvkomi-telegram-control`: мониторинг подключённых серверов и SSH-роутеров, история, ИИ-диагностика и перезапуск разрешённых служб после подтверждения владельца.

Каждый устанавливает своего бота и добавляет свои узлы. Список серверов, SSH-ключи, токены и маршруты создаются при настройке; архив с чужой конфигурацией не нужен. Репозиторий устанавливается только на управляющий сервер. На подключаемый Linux-узел загружается небольшой агент проверок, который запускается по запросу через SSH.

## Установка

На Ubuntu/Debian:

```bash
curl -fsSL -o bot-monitor.tar.gz https://github.com/vikrk/bot-monitor/archive/refs/heads/master.tar.gz
tar -xzf bot-monitor.tar.gz
cd bot-monitor-master
sudo bash install.sh
```

Выберите пункт **1**. Установщик спросит имя управляющего сервера, добавит его в мониторинг локально, предложит настроить Telegram-бота и администратора, ИИ и период проверок. После настройки запускаются бот и таймер мониторинга. В конце открывается меню `fleetctl` для подключения ваших серверов.

Telegram-токен можно получить у `@BotFather`. Подходит любой действующий bot token. ID администратора определяется по отправленному в личный чат `/start` или вводится вручную; в настройке вы подтверждаете свой аккаунт. Команды и кнопки принимаются только от назначенного владельца. Один токен следует использовать с одним активным polling-процессом.

## Подключение и изменение узлов

```bash
sudo fleetctl
```

Выберите «Подключить сервер»: введите название, IP/DNS, SSH-логин и порт. После сверки fingerprint введите SSH-пароль в скрытом запросе. Установщик определит доступные службы, предложит профиль проверок, создаст отдельный SSH-ключ и установит его с ограничением по публичному IPv4 управляющего сервера. Пароль не сохраняется. Затем выполняется проверка ключевого SSH/RPC-доступа; только успешно подключённый узел появляется в меню бота и периодическом мониторинге.

Агент работает от выбранного SSH-пользователя. Для управления systemd-службами и чтения закрытых журналов обычно требуется root. На сервере нужен Python3; для root на Debian/Ubuntu он устанавливается при отсутствии.

В пункте «Настроить проверки» для выбранного узла можно задать:

- контролируемые systemd-службы;
- HTTP(S) URL и ожидаемый код ответа;
- TLS/CDN/origin: адрес, порт и SNI, проверку сертификата и срока действия;
- DNS/DoH/DoT-маршруты и количество запросов;
- путь к querylog AdGuard и узел, на котором этот журнал находится;
- точный список служб, перезапуск которых разрешён владельцу через подтверждение в боте.

Нет заданных URL — нет проверки URL. Проверка доступности службы сама по себе не доказывает работу всех её маршрутов: их адреса задаются в профиле.

Если сервер или SSH-доступ изменились, выберите **«Изменить IP/логин/порт и переподключить узел»**. Новый доступ проверяется до отключения старой записи из мониторинга; прежние ключи автоматически не удаляются. Профиль сохраняется и доступен для редактирования. Можно также переименовать или отключить узел. Список и кнопки бота обновляются по текущей конфигурации без жёсткой привязки к именам SPB/NL/DNS и т.д.

## DNS и подтверждение в AdGuard

При добавлении DNS-маршрута укажите транспорт, URL или host/port, название проверки и число запросов (например, 16). Если требуется подтвердить доставку, выберите журнал на этом же или другом подключённом узле. На узле AdGuard укажите действительный путь к `querylog.json`/`querylog.jsonl` и включите журналирование запросов в самом AdGuard.

Для каждого запроса создаётся уникальное DNS-имя. Вывод отдельно показывает, сколько DNS-ответов получено и сколько уникальных запросов найдено в журнале AdGuard. Статус «дошли 16/16» означает обнаружение всех 16 имён в журнале, а не только успешный ответ HTTPS/DoH. Без настройки журнала бот явно сообщает, что подтверждение доставки в AdGuard не включено.

## SSH-роутеры

Пункт «Подключить SSH-роутер» использует тот же ввод доступа и создание ключа. Поддерживаются устройства с POSIX shell, домашним каталогом, `authorized_keys` и SFTP. С Python3 доступен полный профиль; без Python используется небольшой shell-агент для SSH-доступности, RAM, нагрузки и диска. Устройства только с фирменным CLI или без способа установки SSH-ключей требуют отдельного адаптера; наличие SSH само по себе не гарантирует совместимость с Linux-агентом.

Этот вариант подключения роутера не требует переноса домена управляющего сервера или настройки HTTPS heartbeat.

## Бот, ИИ и планировщик

В Telegram доступны `/menu`, `/status`, `/check_all`, `/resources`, `/history`, `/ai_all`, `/cancel`. В меню каждого узла — проверка, журналы настроенных служб и предложения перезапуска из его разрешённого списка. Подтверждение одноразовое и действует 2 минуты. ИИ анализирует проверки и журналы всех подключённых узлов, включая SSH-роутеры, и не выполняет свои предложения автоматически.

Ключ ИИ-провайдера настраивается отдельно:

```bash
sudo rvkomi-ai-setup
```

Укажите HTTPS API URL, доступную модель и свой API-ключ. Секреты хранятся с правами `0600` в `/etc/rvkomi-watchdog`, история — в `/var/lib/rvkomi-watchdog`. В GitHub они не попадают.

Период мониторинга меняется пунктом меню `fleetctl` или командой `sudo rvkomi-monitor-interval`. Оповещение об ошибке отправляется после трёх подряд неуспешных проверок, затем — о восстановлении. Ежедневный таймер предупреждает о приближении окончания сертификатов из настроенных TLS-профилей.

```bash
sudo systemctl status rvkomi-telegram-control rvkomi-extra-monitor.timer
sudo rvkomi-control-verify
```

## Резервная копия и восстановление

Экспорт/импорт зашифрованной runtime-копии — отдельные пункты `fleetctl`. Они нужны для отката или переноса уже настроенной инфраструктуры, а не для обычной установки. Архив содержит ваши настройки бота, профили и закрытые SSH-ключи. При смене исходящего IP после переноса подключитесь заново через пункт изменения доступа: ключи на узлах ограничены прежним IP.

При явном импорте старой копии можно добавить её прежние списки как legacy-агенты с существующими проверками. Эти списки не используются при обычной чистой установке. Пункт 2 корневого установщика сохранён как старый отдельный Server Manager; описанный сценарий использует пункт 1.
